# notifications

Phase 9. `notification.service.js`'s `emit(event, payload)` is called from domain services as a side effect (booking created/technician assigned — `booking/booking.service.js`; payment success/service completed — `technician/job.service.js`'s `collectPayment()`; claim approved — `super-admin/claim.service.js`; escalation raised — `super-admin/escalation.service.js`) rather than those services constructing `Notification` docs themselves — one place owns what each event actually says. **Never throws**: an unknown event or a template/DB failure logs and returns `null`, so a bug in a notification template can never break the domain action that triggered it. Real-time delivery pushes to the recipient's `user:<id>` socket room (or `broadcast:<role>` for platform-wide ones) via `../../sockets/io.js`'s `getIO()`; `GET /notifications` is the REST fallback/history read. **Device push has two paths**: `deliverExternal()` resolves one `User` and covers push/SMS/WhatsApp for personally-addressed notifications, while `deliverBroadcastPush()` fans a role-wide push out across the whole audience — it pages users by `_id` (never `skip`), drops explicit opt-outs via a single `NotificationPreference` query rather than one lookup per user, and chunks tokens into 500s because `sendEachForMulticast` rejects more than that in one call. `sendAdHocPush()` takes an optional `channels` array: the in-app record (DB row + Socket.IO) is always written because it *is* the broadcast's record and the composer's history reads it back, while `'push'` is what additionally fans out to device tokens — so `['inapp']` is an announcement that shows in the app without buzzing every phone. Omitting it means both, so existing callers are unaffected. Only `sendAdHocPush()` (the console composer, where a human picked the audience) triggers the broadcast fan-out, and it does so **detached** — the admin's request returns before a large fan-out finishes; `awaitPendingDeliveries()` is the hook tests and shutdown use to wait it out. `emit()`'s broadcast templates (escalation, brand warranty claim) stay in-app on purpose: an ops escalation should not ring every phone on the platform. **Who a broadcast audience means** is settled once in `../../config/constants.js` (`BROADCAST_ROLE_FILTER`, `broadcastAudiencesForRole()`) because three layers have to agree on it — the push fan-out, the inbox query in `listNotifications()`, and which `broadcast:<audience>` room a socket joins in `../../sockets/index.js`. They drifted before: the socket layer joined only `broadcast:All` and `listNotifications()` hardcoded `broadcastRole: 'All'`, so a role-targeted broadcast reached nobody through any channel. `getNotification()` checks audience membership too — a `Technicians` broadcast is not a customer's to open by id. **Broadcast read state is per user.** A personally-addressed notification carries its own `read` flag (one reader, one flag); a broadcast has many readers, so flipping that flag would mark the message read for the entire role at once. `notificationReceipt.model.js` holds one row per (user, notification) actually read — absence means unread, so the collection grows by what people read, not by audience size. `listNotifications()` is therefore an aggregation, not a `find()`: `read` has to be computed per user via a `$lookup` on receipts *before* it can be filtered, sorted, or paginated on (computing it in JS afterwards would page over the wrong set). That aggregation also has to re-add `id` by hand — the `toJSON` plugin that maps `_id` -> `id` does not run on aggregation output.
