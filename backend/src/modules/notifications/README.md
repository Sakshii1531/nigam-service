# notifications

Phase 9. `notification.service.js`'s `emit(event, payload)` is called from domain services as a side effect (booking created/technician assigned — `booking/booking.service.js`; payment success/service completed — `technician/job.service.js`'s `collectPayment()`; claim approved — `super-admin/claim.service.js`; escalation raised — `super-admin/escalation.service.js`) rather than those services constructing `Notification` docs themselves — one place owns what each event actually says. **Never throws**: an unknown event or a template/DB failure logs and returns `null`, so a bug in a notification template can never break the domain action that triggered it. Real-time delivery pushes to the recipient's `user:<id>` socket room (or `broadcast:<role>` for platform-wide ones) via `../../sockets/io.js`'s `getIO()`; `GET /notifications` is the REST fallback/history read. Broadcast notifications (`recipient: null`, `broadcastRole` set) have a single shared `read` flag, not a per-recipient read receipt — `markRead()`/`markAllRead()` only ever touch personally-addressed ones, a documented schema limitation, not silently mishandled. See BACKEND_CONTEXT.md §3.12 and `../../../docs/DATA_MODEL.md`'s Phase 9 addendum.
